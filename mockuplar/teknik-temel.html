Vercel, Supabase ve R2

Bu yığın sitenin ihtiyacına önceki seçenekten daha iyi oturuyor — ama bir bedeli var ve baştan bilmeniz gerekiyor: Vercel PHP çalıştırmaz. Mevcut kod tabanı kullanılamaz, uygulama TypeScript ile yeniden yazılır. Karşılığında sayfaların çoğu statik üretilir, veritabanına hiç uğramaz ve arayüz belirgin biçimde hızlanır.

Bölüm bir

Bu kararın anlamı

Önceki planla arasındaki fark yalnızca sağlayıcı değişikliği değil; çalışma zamanı ve render modeli baştan değişiyor. İkisi de sizin lehinize, biri maliyetli.

PHP kod tabanı kullanılamaz

Vercel PHP barındırmaz. Mevcut sitenin sunucu tarafı kodu — şablonlar, sorgular, form işleyicileri — tamamen yeniden yazılır. Next.js ve TypeScript ile. Bunu bir kayıp olarak görmeyin: zaten Bootstrap 3 ve jQuery 3.2 üzerine kurulu, 2016 mimarisine sahip bir kod tabanından bahsediyoruz ve tasarım tarafında sıfırdan bir sistem kurduk. Ama iş yükü tahmininizi buna göre yapın — “tasarımı giydiririz” senaryosu bu yığında yok.

Taşınabilen tek şey veri: proje, firma, haber arşivi ve teslim kayıtları. Onlar da zaten yeni şemaya göç edecekti.

Karşılığında iki kazanç

Bir — gecikme neredeyse sıfırlanıyor. Hostinger Hollanda'dan Frankfurt'a ~10 ms vardı. Vercel'in fra1 bölgesi Supabase'in eu-central-1 bölgesiyle aynı şehirde: 1–2 ms. Önceki belgenin yarısı bu 10 ms'yi telafi etmek üzerineydi; o sorun ortadan kalkıyor.

İki — ISR tam sizin siteniz için tasarlanmış gibi. Sayfalarınızın çoğu nadiren değişiyor: bir proje detayı ancak firma fiyat güncellediğinde değişir. Next.js bu sayfaları statik üretip kenarda tutuyor ve yalnızca o proje onaylandığında yeniden üretiyor. Tasarımda “etiketli önbellek temizleme” diye anlattığım mekanizmanın yerleşik hali.

Bölüm iki

Mimari

İki ayrı yol var ve birbirine hiç değmiyor: HTML yolu Vercel'den, medya yolu doğrudan R2'den geçiyor. Medyanın Vercel'e uğramaması bilinçli bir karar — sebebi altıncı bölümde.

Kritik nokta: medya hiçbir zaman Vercel'den geçmiyor. Vercel bant genişliğini faturalandırır ve görsel trafiği o kotayı hızla yer. Kendi alt alan adınızla R2'den servis edildiğinde Vercel bu trafiği hiç görmez.

Etiketli yenileme

Yönetim panelinde bir proje onaylandığında tüm siteyi değil, yalnızca o projeye bağlı sayfaları yeniden üretin. Tasarımda anlattığım hedefli temizleme tam olarak bu: 

// app/api/onay/route.ts — onay kuyruğunda "Onayla" basıldığında
import { revalidateTag } from 'next/cache';

export async function POST(req: Request) {
  const { projeId, ilce, il, firmaSlug } = await onayla(req);

  // yalnızca etkilenen sayfalar yeniden üretilir
  revalidateTag(`proje-${projeId}`);        // detay + kat planı sayfaları
  revalidateTag(`ilce-${ilce}`);            // ilçe sayfası ve listeleri
  revalidateTag(`il-${il}`);                // şehir sayfası ortalamaları
  revalidateTag(`firma-${firmaSlug}`);      // firma portföyü

  return Response.json({ ok: true });
}

// app/[il]/[ilce]/[slug]/page.tsx — veri çekerken etiket verilir
const proje = await fetch(url, {
  next: { tags: [`proje-${id}`, `ilce-${ilce}`] }
});

Tüm siteyi temizlemeyin

revalidatePath('/', 'layout') gibi geniş bir temizleme her onaydan sonra 4.800 sayfayı geçersiz kılar. Ertesi gün ilk ziyaretçiler soğuk sayfalara düşer, her biri veritabanına gider ve mimarinin tüm faydası kaybolur. Her yenileme hedefli olmalı ve hangi etiketlerin tetiklendiği denetim günlüğüne yazılmalı.

Bir uyarı daha: 1.240 proje × ortalama 4 daire tipi + bölge sayfaları toplamda 5 bine yakın statik sayfa demek. Vercel'de ISR önbelleğinin plan bazlı bir üst sınırı var; kurulumdan önce güncel belgeden teyit edin. Sınır sorun çıkarırsa kat planı sayfalarını ISR yerine kenar önbellekli dinamik yapmak en kolay tavizdir.

Bölüm dört

Veritabanı bağlantısı

Serverless'ta bağlantı yönetimi en sık batırılan konu. Fonksiyonlar anlık olarak yüzlerce örneğe çıkabilir; her biri doğrudan Postgres'e bağlanmaya çalışırsa bağlantı havuzu dolar ve site komple durur. 

// lib/db.ts
import postgres from 'postgres';

// Modül kapsamında tek istemci — sıcak fonksiyon örnekleri arasında yeniden kullanılır
export const sql = postgres(process.env.DATABASE_URL!, {
  prepare: false,        // ZORUNLU: transaction-mode havuzda prepared statement çalışmaz
  max: 1,                // serverless örneği başına tek bağlantı
  idle_timeout: 20,
  connect_timeout: 10,
});

// .env — iki ayrı URL tutun
DATABASE_URL="postgres://...@aws-0-eu-central-1.pooler.supabase.com:6543/postgres"
DIRECT_URL="postgres://...@aws-0-eu-central-1.pooler.supabase.com:5432/postgres"
// 6543 → uygulama · 5432 → göçler, pg_dump, CREATE INDEX CONCURRENTLY

Bölüm beş

Zamanlanmış işler: çoğu Postgres'in içinde

Vercel fonksiyonlarının çalışma süresi sınırlı. REFRESH MATERIALIZED VIEW gibi işler bu sınırı aşabilir ve yarıda kesilir. Çözüm: veritabanı bakımını veritabanının içinde çalıştırmak. 

-- Supabase'de pg_cron etkinleştirilir
create extension if not exists pg_cron;

-- Gecelik: materyalize görünümler
select cron.schedule('mv-yenile', '0 2 * * *', $$
  refresh materialized view concurrently mv_ilce_m2;
  refresh materialized view concurrently mv_firma_karne;
$$);

-- Saatlik: 90 gün tazelik kuralı
select cron.schedule('tazelik', '0 * * * *', $$
  update proje set fiyat_teyit_durumu = 'teyit_edilmedi'
  where fiyat_teyit_tarihi < current_date - interval '90 days'
    and fiyat_teyit_durumu <> 'teyit_edilmedi';
$$);

-- Gecelik: teslim tarihi geçen projeleri arşive al
select cron.schedule('arsivle', '30 2 * * *', $$
  update proje set durum = 'arsiv'
  where durum = 'satista' and teslim_tarihi < current_date - interval '3 months';
$$);

Bölüm altı

Medya akışı

20 GB'lık görsel ve belge arşivi R2'de. İki kural var ve ikisi de Vercel'e özgü kısıtlardan doğuyor.

Yükleme doğrudan R2'ye

Vercel fonksiyonlarının istek gövdesi sınırlıdır; 4 MB'lık bir render bu sınırı aşar.

  • Fonksiyon yalnızca imzalı URL üretir
  • Tarayıcı dosyayı doğrudan R2'ye yükler
  • Yükleme bitince fonksiyona kayıt bildirilir
  • Dosya hiçbir zaman fonksiyondan geçmez

Varyantlar kenarda

Vercel'in görsel optimizasyonu kaynak görsel başına ücretlendirilir; bu ölçekte pahalı.

  • Cloudflare Images veya Bunny Optimizer
  • 320 / 640 / 1280 / 2400 px · AVIF + WebP
  • Next <Image> için özel loader
  • unoptimized değil — loader ile yönlendirin

Orijinal asla servis edilmez

20 GB'ın büyük kısmı soğuk veri; yalnızca varyant üretiminin kaynağı.

  • Orijinaller ayrı önek altında
  • Kat planı: PDF + PNG önizleme
  • R2'de sürümleme açık
  • Alt metni olmayan dosya yayınlanamaz
// next.config.ts — görselleri Cloudflare Images üzerinden servis et
export default {
  images: {
    loader: 'custom',
    loaderFile: './lib/imageLoader.ts',
  },
};

// lib/imageLoader.ts
export default function loader({ src, width, quality }) {
  const params = [`width=${width}`, `quality=${quality || 75}`, 'format=auto'];
  return `https://cdn.konutprojeleri.com/cdn-cgi/image/${params.join(',')}/${src}`;
}

Klasör yapısı önceki belgeyle aynı kalıyor: projeler/{id}/gorsel/, projeler/{id}/plan/, projeler/{id}/santiye/{yyyy-mm}/, firmalar/{id}/, haber/{yil}/. Veritabanında yalnızca anahtar ve alt metin tutulur.

Bölüm yedi

Şema ve yetkilendirme

Veritabanı şeması sağlayıcıdan bağımsız — önceki belgede tanımladığım tablolar aynen geçerli. Değişen tek şey yetkilendirme katmanı: Supabase Auth devreye girdiği için satır seviyesi güvenlik (RLS) artık kullanılabilir.

Değişmeyen kurallar: fiyat_kaydi ve denetim_gunlugu tablolarında UPDATE ve DELETE yetkisi iptal edilir; m2_birim hesaplanan sütundur; ozellikler jsonb + GIN indeksiyle 60 filtreyi taşır; konum geography(Point,4326) ve GIST indeksli. 

-- Firma paneli: firma yalnızca kendi projesini görebilir ve düzenleyebilir
alter table proje enable row level security;

create policy firma_kendi_projesi on proje
  for select using (
    firma_id = (auth.jwt() ->> 'firma_id')::bigint
    or auth.jwt() ->> 'rol' in ('admin','editor')
  );

create policy firma_kendi_projesini_duzenler on proje
  for update using (
    firma_id = (auth.jwt() ->> 'firma_id')::bigint
  ) with check (
    -- firma yayına alamaz; yalnızca taslak ve onay kuyruğu
    yayinda = false
  );

-- Talepler: firma yalnızca kendisine iletilen talebi görür
create policy talep_firma on talep
  for select using (
    firma_id = (auth.jwt() ->> 'firma_id')::bigint
  );

RLS'yi tek savunma katmanı saymayın

Sunucu bileşenleri servis rolüyle bağlanırsa RLS devreye girmez; yetki kontrolü uygulama kodunda yapılır. RLS burada ikinci katman: bir uygulama hatası veya yanlış yapılandırılmış istemci çağrısı olduğunda veriyi korur. Servis rolü anahtarı yalnızca sunucu tarafında bulunmalı, NEXT_PUBLIC_ önekiyle asla tanımlanmamalı.

KVKK — şemaya şimdi girmesi gereken tablo

Supabase Frankfurt demek, talep formundaki ad ve telefonun Almanya'da tutulması demek. Açık rıza metnini yurt dışı aktarımını kapsayacak şekilde yazdırın ve onay kaydını veritabanında tutun — metin sürümü, zaman damgası, IP. Sonradan eklemek çok daha zor. 

create table kvkk_onay (
  id            bigserial primary key,
  talep_id      bigint references talep,
  metin_surumu  text not null,      -- 'v1.2 · 2026-08-01'
  metin_hash    text not null,      -- o anki metnin özeti
  onay_zamani   timestamptz not null default now(),
  ip            inet,
  user_agent    text
);
revoke update, delete on kvkk_onay from app_rw;

Hukukçu değilim; metinleri ve aktarım evrakını bir avukata hazırlatın. Ama tabloyu şimdi koyun.

Özet

Bu yığın sitenin ihtiyacına iyi oturuyor: SEO ağırlıklı, nadiren değişen, çok sayfalı bir içerik sitesi ISR için ideal. Gecikme sorunu ortadan kalkıyor, ölçeklenme sizin işiniz olmaktan çıkıyor.

Karşılığında ödediğiniz bedel net: uygulama sıfırdan TypeScript ile yazılıyor. Bunu bir gecikme değil, zaten verilmiş bir kararın sonucu olarak görün — tasarım sistemini de sıfırdan kurduk. Ama planlamayı buna göre yapın: bu belge 12–16 haftalık bir iş tarif ediyor, “tasarımı giydirme” işi değil.

Bu belge, Hostinger Cloud için hazırlanan birinci sürümün yerini alır. Şema, veri kuralları ve medya klasör yapısı değişmedi; çalışma zamanı, render stratejisi, bağlantı yapılandırması ve zamanlanmış iş yerleşimi değişti.

Sağlayıcı limitleri, port adresleri, bölge kodları ve fiyatlar zamanla değişir; kurulum sırasında güncel belgelerden teyit edin. KVKK bölümü bilgilendirme amaçlıdır, hukuki görüş değildir.
